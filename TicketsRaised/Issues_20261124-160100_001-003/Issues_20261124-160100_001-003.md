## ISSUE 001: A sign-in / create-account wall on Workday is reported as `FORM NOT FOUND`

**Severity:** high. The job is mis-classified and mis-counted. The user is told "no form" when the real reason is "this site needs an account".

**What happens**
1. Workday is not one of `STANDARD_VENDORS` (greenhouse, lever, ashby). `assist.py` ~L636-653 therefore sends it to the form agent: `page.goto(direct)`, then `agent.run("reach")`.
2. `formagent.run("reach")` stops with `outcome="need_user"` on Workday's account page. Two code paths do it:
   - `formagent.py:734-735`: `snap.has_password and not snap.has_form()` gives "a sign-in page: the agent never signs in or creates an account".
   - `_reach()` at ~L887: the same message.
   The agent's own message is printed (`form agent: need_user: ...`), but it is only in the log.
3. `assist.py` ~L652-653 throws that reason away:
   `problem = None if reached.outcome == "reached_form" else f"FORM NOT FOUND {direct}"`.
   Any outcome other than `reached_form` (need_user, limit, sign-in wall, no Apply link) becomes the same text, `FORM NOT FOUND <url>`.
4. `count(problem)` records it in `data/live/submit_failures.csv` as `form_not_found`. After 2 such rows `max_submit_failures` hands the job off, with the wrong reason.
5. The live report says `ready_not_submitted`, with no sign that an account is needed.

**Expected**
A Workday account wall should end as an account-required outcome, not a form-not-found failure:
- status `manual_apply_account_required` (`route.ACCOUNT_STATUS`), printed with `route.account_line(...)`;
- no failure row, because nothing is wrong with the form;
- the apply pack (CV, letter, `answers_to_paste.txt`) offered, so the user can create the account in their own browser.

**Root cause**
`route.require_no_auth` (→ `errors.AccountRequired`) is only called from `formfind.wait_for_form`, which the agent branch never uses. The agent branch reports its own `need_user` outcome as `FORM NOT FOUND`. Nothing maps "agent saw a password field" to `AccountRequired`.

**Fix direction (for the implementing model)**
- In `assist.py` (agent branch) and its autoapply counterpart, keep `reached.reason`.
  If it is a sign-in / account reason, `raise AccountRequired(reason, url)`. This is already handled at `assist.py` ~L701 via `account_required(...)`.
  Only a real "no Apply link / no fields" case stays `FORM NOT FOUND`, and it should print the agent's reason.
- Do not call `count(problem)` for account walls.
- Add a regression test in `tests/apply/` using a fake Workday page with a password field: expect `AccountRequired`, status `manual_apply_account_required`, no row in `submit_failures.csv`. Tests must use `tmp_path`, with no network and no LLM.

## ISSUE 002: Workday's multi-step entry (Apply, then "Start Your Application", then Create Account) is not modelled

**Severity:** medium. This is the reason the wall is reached at all, and it is an inference to confirm.

**Likely sequence on `*.myworkdayjobs.com`** (confirm in the other terminal):
1. Job page: an `Apply` button (`data-automation-id="adventureButton"`).
2. Modal "Start Your Application": Autofill with Resume / Apply Manually / Use My Last Application.
3. "Create Account / Sign In" page: email, password, verify password, a "create account" consent checkbox.
4. Only after sign-in: the real "My Information" form.

**Gaps**
- `REACH_CLICKS` (`formagent.py` ~L59) clicks "Apply Manually", then "Apply". Step 3 has a password field and `SIGN_IN` deliberately blocks the buttons, so the run correctly stops there. The application form cannot be reached without an account, so the agent is right to stop.
- There is no Workday-specific knowledge anywhere in `apply/`. `ats_vendor.direct_url` returns the job URL unchanged.
- Workday is a slow single-page app. `SETTLE_MS = 2500` may be too short for the modal, which could produce a false "no way in" on a good run. Check the agent log.

**Fix direction**
- Treat Workday as "account required, known up front". Before opening a browser, skip straight to the hand-off for hosts `myworkdayjobs.com` / `myworkday.com` / `myworkdaysite.com` (use `ats_vendor.vendor_of(url) == "workday"`).
  `settings.yaml` already keeps a `handoff_hosts` list for this (`jobs.lever.co`). Either add the host there (the user's file) or, better, make the vendor a built-in default.
- Keep the hard rules: never create an account, never sign in, never retry a third time.

## ISSUE 003: Hand-off for an account wall gives the user too little

**Severity:** low to medium (quality of life).

**What happens:** the live report (`data/live/20261124-155356.md`) shows `status: ready_not_submitted` with no note that an account is needed. For account walls the run should say so in the report.

**Expected**
- The report line reads `manual_apply_account_required: Workday needs an account (create it yourself)`.
- `answers_to_paste.txt` is written in the job's output folder, so the user can finish quickly after creating the account.
- The listing URL is shown, and the tracker status reflects it.

**Fix direction:** reuse `handoff.py` (the `answers_to_paste.txt` writer) and `route.account_line`. No new dependencies.

## Fixed (001, 002, 003) — 24 Nov 2026

All three tickets are fixed in `careerops/apply/` with tests in `tests/apply/test_workday_account.py`:

- **001** — A sign-in / create-account wall on Workday is `manual_apply_account_required`, never `FORM NOT FOUND`. `formagent.SIGN_IN_NEED` names the reason; `assist.py` agent branch and its fallback raise `AccountRequired` on it; `planned.py` calls `route.require_no_auth(page)` before declaring `FORM NOT FOUND`. No failure row is written.
- **002** — Workday's multi-step entry is modelled: `planned.py` passes the form agent to `formscan.reach`, so the agent clicks `Apply` / `Apply Manually` (never `Sign In` / `Create Account`, types nothing), then stops at the account page.
- **003** — `assist.account_required(..., pack=...)` builds the apply pack and opens the listing via `Handoff.run(remember=False)`; `live._account_required` ends the job `manual_apply_account_required` with the listing printed.

New tests: 5 in `tests/apply/test_workday_account.py`. Existing apply tests unchanged (Greenhouse path is unaffected).

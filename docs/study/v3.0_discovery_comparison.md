## Phase A — answers, with evidence

### A1. How does career-ops find jobs at companies the user never listed?

**Two separate mechanisms. Only the second is code.**

1. **`search_queries` are run by the AI agent's own WebSearch tool, not by any program.**
   - `portals.example.yml:829-833`: "Each query triggers a WebSearch. Use site: to filter by portal."
   - `modes/scan.md:5`: the WebSearch levels "represent the **agent** workflow (executed by the AI agent), not what `scan.mjs` does."
   - `modes/scan.md:166-176` (Level 3) and `:219-227` (step 6): the agent runs each enabled query, then extracts `{title, url, company}` from result titles (`" @ "` / `" | "` splitting).
   - `verify-portals.mjs:267-270`: "A `search_queries` entry only produces links for a human to open; it never feeds the zero-LLM scanner."
   - `scan.mjs` never reads `search_queries` (grep over all `*.mjs`: only `coverage-check.mjs:165`, `validate-portals.mjs:201,476`, `verify-portals.mjs`).
   - **Backend:** whichever search tool the host CLI has (Claude Code WebSearch, etc.). There is no search API client in the repo. **It cannot run without an LLM agent.**
   - `modes/scan.md:170` admits the weakness: "Level-3 hits can be weeks stale… a Level-3 snippet is never proof a role is still open."
   - The only code that touches query text is `verify-portals.mjs --unmined` (`:267-290`, `:1043-1119`): it extracts company names from queries and probes Greenhouse/Ashby/Lever **slugs** for them.
2. **Reverse sweep of a public dataset of boards** (`scan-ats-full.mjs`, zero LLM).
   - `:29-32`: company directories come from `github.com/Feashliaa/job-board-aggregator` (+ join.com's own sitemap), cached 24 h (`:99`).
   - Files read: `greenhouse/lever/ashby/workday/icims/bamboohr/paylocity_companies*.json` (`:344-420`).
   - It then walks **every board in the dataset** with the same providers as `scan.mjs`, keeps postings that pass `title_filter`/`location_filter` and have a publish date within `--since` days (default 3).
   - Extra seeds: VC portfolio lists (`seeds/vc-portfolios.mjs`, `seeds/README.md`), and boards derived from the user's own tracker/history URLs (`history-ats-seeds.mjs`).

So career-ops finds *new companies* by (a) an agent searching the web and (b) **downloading someone else's list of 20,000+ board slugs**, not by guessing.

### A2. How is a provider picked from a `careers_url`? Does it guess slugs?

- **Picking:** `providers/_registry.mjs:68-97`. Order: explicit `provider:` → `local-parser` → every provider's `detect(entry)` in alphabetical file order, first hit wins. `scan.mjs:4412` calls it; an entry no provider claims is skipped and counted (`:4413-4422`), and only `scan_method: websearch` entries are handed to the agent (`:4415-4421`, `:5267-5274`).
- **`scan.mjs` never guesses.** A `tracked_companies` entry must carry a `careers_url` (or `api:`). Several providers state "never guesses": Collage (`SUPPORTED_JOB_BOARDS.md:30`), Comeet (`:31`), Gem (`:50`).
- **But career-ops does guess in one tool, on request:** `discover-ats.mjs`.
  - `deriveSlug` lowercases the name and hyphenates it (`:170-175`).
  - It probes **11 vendors** in a fixed order, first hit wins (`VENDOR_ORDER`, `:120`; `buildCandidateUrls`, `:256-309`), with `DEFAULT_CONCURRENCY = 8` (`:72`).
  - It is **preview-only by default**, writes to `portals.yml` only with `--write` (`:10-19`), and runs for a handful of names the user (or the agent, by the `_custom.md` house rule, `KEEPING_PORTALS_LIVE.md:25-54`) hands it.
- **So why does it not get rate-limited the way we do?** It does get throttled; it just *meets the problem differently*:
  - The comment at `scan-ats-full.mjs:113-120` records exactly our failure: with 20 connections, Lever's "unreachable" count went 2,436 → 4,100 and Ashby's 683 → 1,675 "the boards were never dead — they were refused". The fix was to cut single-host concurrency to **6** (`:121`), Paylocity and join.com to **2** (`:126`, `:132`).
  - Guessing is **bounded by use**: a few names, once, then the answer lives in `portals.yml`. We guess ~4 tokens × 4–9 providers × every company, every run, and re-ask misses after 30 days.
  - **Misses need evidence:** `dead-boards.mjs:7-9`: a board is only "dead" after **3 real HTTP 404s** and is re-checked after 30 days; "throttles, transport failures and DNS errors mean unknown, never dead" (`:2-3`).
  - It has no robots.txt step at all in code (see A6), so it cannot be refused *by robots*; it is refused by status codes and handles those with backoff.

### A3. How do `job_boards` differ from `tracked_companies`?

- `portals.example.yml:3417-3422`: `tracked_companies` = one entry per employer; `job_boards` = "multi-employer aggregators… return offers from many companies in a single API call. Same title/location filtering and dedup apply."
- Routing is identical (`scan.mjs:4350`, `resolveEntries(isBoard)` at `:4402-4433`); the difference is the *company is read from each posting*, and board-wide providers have no `detect()` (explicit `provider:` needed: Built In `SUPPORTED_JOB_BOARDS.md:25`, Arbeitnow `:17`, The Hub `:128`, Landing.jobs `:84`).
- **VC portfolio boards (Getro, Consider) are boards, but per-tenant:** not auto-detected; you give `provider: getro|consider` + the board's `/jobs` URL (`:34`, `:53`). One entry then returns every portfolio company's postings (Atomico, Balderton, Notion Capital are named in the docs). This is the closest thing career-ops has to "jobs at companies you never listed" for the EU.

### A4. Location, country eligibility, visa: what do they read, and what if a field is missing?

| Filter | Reads | Missing data | Evidence |
|---|---|---|---|
| `location_filter` | the provider's **structured location** + a hint from the URL path; never the JD body | empty → **pass** (unless `strict: true` with a restricting tier). Order: `block_hard` > `always_allow` > `block` > `allow`; `remote_title_fallback` rescues "Remote" titles | `scan.mjs:665-721` |
| `country_eligibility_filter` | the **JD body** (`description`) for exclusionary phrases ("must be located in…") unless an inclusive phrase or the candidate's own country is named | no description → **pass**; no exclusionary phrase → pass; candidate in the US → filter off | `:940-1009` |
| `visa_filter` | the **JD body**. A `negative` phrase rejects; with `require_mention: true` a `positive` phrase is required | no description → pass (`require_mention: false`) or **reject** (`true`). Defaults already include **UK Skilled Worker** and **EU Blue Card** wording | `:1011-1111`, defaults `:1035-1090` |
| `content_filter`, `experience_filter` | JD body | pass | `:901`, `:4382-4387` |
| `max_posting_age_days` | provider `postedAt` | no date → pass | `:729` |

All five are built once in the main routine (`:4362-4387`). Only providers that return `description` in the list payload give the three JD-body filters anything to read; the rest pass everything.

### A5. How is the list kept fresh and re-fetching avoided?

- **Company list:** a *house rule*, not code: `modes/_custom.md` tells the agent to run `discover-ats.mjs` for any company that comes up and append it (`KEEPING_PORTALS_LIVE.md:25-54`). Checks: `validate-portals`, `verify-portals`, `audit-portals` (`no-provider` / `empty` / `error`, with a `--baseline` to catch ATS migrations), `filter-audit`, `coverage-check` ("why did the scanner miss this posting?", `:132-154`).
- **Scan history** (`data/scan-history.tsv`): URLs are deduped on `normalizeUrlForDedup` (`scan.mjs:1826`). Statuses decide whether a URL stays pinned: `added`/`skipped_expired` are released by `recheck_after_days`; `skipped_invalid_url`/`skipped_blocked_host` are permanent; the "observational" ones (`skipped_title/location/age/content/visa/…`) **never pin**, so widening a filter hands the postings back at zero cost (`:1546-1669`, `:1671-1677`).
- **Strong dedup key:** `listing-fingerprint.mjs` / `docs/listing-fingerprint.md`: SHA-256 of `ats_provider + board_slug + posting_id`; used for Greenhouse/Ashby/Lever (`docs/listing-fingerprint.md:1-12`). `url-key.mjs:1-45` strips only a denylist of tracking params and says why ("under-strip on purpose"). `detect-reposts.mjs:1-45`: reposts need ≥ 2 distinct URLs on ≥ 2 distinct scan dates from the **same source**.
- **Liveness ladder:** `liveness-api.mjs:1-35`: ATS JSON endpoint first (per-job for Greenhouse/Lever/Workday; board listing for Ashby), browser only when inconclusive; "expired" only on a definitive signal. Dead postings are written back to the history as `skipped_expired` (`AGENTS.md`, `check-liveness.mjs` row).
- **Ids that cost a request** (Getro collection id, Jobvite eId…) are cached 30 days (`providers/_cached-lookup.mjs:22-36`). That cache holds *positive* answers; negative caching is `dead-boards.mjs`.

### A6. Rate, politeness, caching, retries

- **Per-request:** `providers/_http.mjs`: redirects are **refused** by default (`:141-144`); `RETRY_DEFAULTS = {retries: 2, baseDelayMs: 500, maxDelayMs: 8000}` (`:548`); jitter 250 ms (`:538`); 429, any 5xx and transport errors are retried, **other 4xx never** (`:641-664`); `Retry-After` is honoured but capped at 4 × `maxDelayMs` = 32 s (`:723-726`).
- **Pacing:** per-page delays of 150–250 ms are "the norm", 750 ms where throttling was seen, 2100 ms for a published 30 req/60 s limit; a robots `Crawl-delay` is "a reasonable floor" (`ADDING_A_PROVIDER.md:530-554`).
- **Parallelism:** `SCAN_CONCURRENCY = 32` total, `HOST_CONCURRENCY = 10` per host (`scan.mjs:161-162`, `:4914-4915`). **There is no 1 request/second per host rule.** Reverse sweeps: 20 / 6 / 2 (above).
- **robots.txt is a human review step, not code.** `CONTRIBUTING.md:148` (rule 6): checked "before a provider is written", per path, and a rule naming only `ClaudeBot`/`anthropic-ai` "does **not** name this client" (a maintainer decision). `_http.mjs`, `scan.mjs` and `liveness-core.mjs` contain no robots check; the 25 provider files that mention robots.txt do so in comments that record the check the author did by hand (e.g. `platsbanken.mjs:24`, `homerun.mjs:45`).
- **Identity:** an honest UA (`user-agent.mjs:13`), **but 21 provider files use `BROWSER_LIKE_USER_AGENT`** (`user-agent.mjs:15-22`: "for callers that must clear WAF/CDN bot management blocking the plain career-ops UA outright"): Workable, Workday, Eightfold, iCIMS, JazzHR, Taleo, Oracle, PeopleSoft, Platsbanken, Getro, Consider, Built In, … The Workable provider also "carries browser-like headers" (`SUPPORTED_JOB_BOARDS.md:136`), WTTJ sends a forged `Referer` (`providers/wttj.mjs:8-9,230`), and Dayforce/Interamt drive a real browser. **None of this may be ported** (your rule: no forged UA/Referer/cookies).
- **Connection pools:** one pool per board in sweeps, closed after (`_connection-scope.mjs:1-30`) because tens of thousands of idle sockets broke later stages.
